================================================================================
PART 5 — THE SINGLE MOST ACTIONABLE FINDING
================================================================================

We have spent four work sessions building Families A, B, C, D, E into the
runtime. The features are technically correct, well-tested, and sit on
the trade-decision path. **But because trade-decision events are rare
(zero yesterday, ~5/week on a good week), we are accumulating fill-model
data at a glacial pace.**

At the current rate of fills (~5/week), we need ~10-20 weeks before any
of the Family A-E reliability diagrams have enough data to inform model
training. The fill-model design doc specifically calls this out as an
open risk.

Recommendation: **capture Family A-E features on a SAMPLE of the skip
path too.** Specifically, on every candidate that passes through the
"final-stretch" gates (gate_min_edge, gate_fv_saturation, gate_fv_ask_gap,
gate_blowout, gate_s2_suppress) but ultimately skips. These are the rows
that look LIKE potential trades and would give us labeled "did this
signal end up over the line?" data — the same data we get from the
existing outcomes JSONL.

Concretely: in signal_pipeline.py, after a skip caused by one of those
specific late-stage gates, also call _start_tape_capture, _start_family_b
_capture, _start_family_c_capture, and the inline D/E computations.
Persist with a "decision=skip_with_features" marker on the candidate row.

Performance impact: the early-gate skips (gate_min_inning, gate_min_entry
_ask) which represent 88% of skips would NOT trigger feature capture —
so we don't add 7,000+ HTTP calls per day. Only the ~250-300 late-stage
skips per day would, adding ~50 seconds of HTTP load over the full
session — trivial.

Data benefit: we'd jump from ~5 fill-model-relevant rows per week to
~250-300 per day. That changes the fill-model training timeline from
"6 months" to "2 weeks."

Caveat: Family A-E on skip rows are not perfect substitutes for fill
data — we don't observe a fill outcome, just a counterfactual ("would
have won if filled"). But:
  (a) the existing outcomes pipeline already tracks counterfactuals
  (b) the fill-model needs both filled AND non-filled examples — skip
      rows ARE non-filled examples by construction
  (c) for M_win_if_filled, we can still use only the filled subset
      (slow accumulation), but for M_fill we now have a much larger
      training set

PART 6 — SECONDARY FINDINGS / SMALLER IMPROVEMENTS
================================================================================

6.1 Universe is small (10 markets). Investigate market filter.
    Yesterday only 8 games / 10 (game, line) pairs got monitored. MLB
    typically has 15+ games per night. Either:
       (a) Sunday slate is genuinely smaller (plausible — Sunday is
           often only afternoon games)
       (b) some games started before the bot launched (21:48 UTC =
           17:48 ET, after first pitch for east-coast games)
       (c) market filter is excluding too aggressively
    Resolution: log INFO at startup with the full list of (game, line)
    pairs the bot decided to monitor and WHY any were excluded.

6.2 Calibrator is loaded as identity-method.
    fair_value_calibration_method='identity' on all 238 shadow scores.
    Means the calibrator JSON loaded successfully but contains no actual
    Platt/isotonic transformation. Check whether the calibration training
    job (analyze_polymarket_calibration or similar) is actually producing
    a non-trivial model. If not, calibration is a placeholder consuming
    log lines but doing nothing.

6.3 Tick-buffer health is unknown.
    Family C reads from LineState.tick_buffer which I wired to populate
    every tick (before the early returns). With no bets fired, we can't
    confirm from outputs alone that the buffer is being maintained.
    Easy fix: add an INFO log every 10 minutes per LineState showing
    `tick_buffer length, oldest age, newest age`. If buffer is stuck at
    1 entry or empty, we have a wiring bug.

6.4 The 15.8 MB candidate-row file size deserves investigation.
    100x growth vs prior days on a similarly-zero-bet day. Suggests
    either:
       (a) shadow_relaxed_* fields were added as nested dicts on every
           skip row (~14 new keys per row * 7,681 rows = significant)
       (b) something else is bloating per-row payload
    Not blocking — but if disk fills up over a week, we'll regret not
    investigating. Spot-check row sizes when convenient.

6.5 Conditional-relax sample of 13 is too small to learn from.
    The blowout-relax rework only fired 13 times yesterday. Need many
    more cases before we can evaluate whether it's letting through good
    signals or bad ones. Continue running, evaluate after ~50-100 cases.
