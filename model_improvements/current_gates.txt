GATE 1: Inning filter
  File: signal_engine.py
  Param: --min-inning (default 4), --min-inning-high-line (default 5)
  Param: --high-line-cutoff (default 8.5)
---------------------------------------------------------------------------

Rule:
  Standard lines (<8.5): skip signal if inning < 4.
  High lines (>=8.5): skip signal if inning < 5.

Why:
  Early-inning signals have too many remaining scoring opportunities, producing
  noisy ask jumps from baserunner situations that don't score, pitching changes,
  etc. The Poisson FV at inning 2-3 is insensitive to inferred single runs
  because there are 12-14 half-innings still to play. Edge detection works best
  when the game state is specific enough to produce meaningful FV changes.

  High-line cutoff (>=8.5): lower base probabilities mean one more inning of
  data (inning 5) filters out games where the offense has stalled.

Data:
  No live data below inning 4 (gate in place from session 1).
  Backtest showed inning 1-3 signals had win rates below 60%, well short of
  the ~76% break-even for typical ask levels.
  Shadow data (2026-04-22 to 2026-04-24): Gate 1 session-level counts show
  moderate volumes of early-inning blocks.
  Apr 27 instrumentation update: Gate 1 now writes skip candidate rows before
  returning, including effective inning threshold and shadow-relaxed metadata.


---------------------------------------------------------------------------
GATE 2: Inactive inning state
  File: signal_engine.py
  No CLI param (hardcoded: {"end", "middle"})
---------------------------------------------------------------------------

Rule:
  Skip if inning_state is "end" or "middle" (between-half transitions).

Why:
  During "middle" and "end" states no active at-bat is happening, so no run
  can be scored. A price jump during these states reflects market participants
  reacting to the score that JUST happened (already priced in), not an active
  event we can trade on.

GATE 3: Minimum entry ask
  File: signal_engine.py
  Param: --min-entry-ask (default 0.55), --min-entry-ask-high-line (default 0.60)
---------------------------------------------------------------------------

Rule:
  Standard lines: skip if ask < 0.55.
  High lines (>=8.5): skip if ask < 0.60.

Why:
  Low-probability markets (ask < 0.55) have thin order books, making limit
  orders more vulnerable to adversarial selection. The ask floor also prevents
  entering long-shot positions where even a win generates marginal EV.

GATE 4: Spread filter
  File: signal_engine.py
  Param: --max-spread (default 0.20)
---------------------------------------------------------------------------

Rule:
  a) Crossed/locked book: skip if bid >= ask.
  b) Wide spread: skip if (ask - bid) > 0.20.

Why:
  Crossed book = data error or anomaly. Wide spread = no consensus on fair
  value, amplifying limit-price positioning error. Our formula
  (bid + spread * 0.65) places us inside the spread, but if spread=0.30
  we could end up 10-15c above informed participants' estimate of fair value.

Data:
  All profitable historical fills had spreads of 0.02-0.06.
  DET@CIN 2026-04-24: spread=0.060 (bid=0.73, ask=0.79) — clean book.
  PHI@CHC 2026-04-23: spread=0.040 (bid=0.65, ask=0.69) — clean book.

GATE 5: Confirmed sustained ask jump
  File: signal_engine.py
  Param: --jump-threshold (default 0.06), --confirmation-ticks (default 3)
  Param: --lookback-ticks (default 5)
---------------------------------------------------------------------------

Rule:
  Fire only when the ask has risen >= 0.06 (6c) over the last 5 ticks AND
  the ask has stayed elevated for 3 consecutive ticks (confirmation window).
  If the ask drops below 50% of the original jump magnitude during those 3
  ticks, the pending signal is cancelled.

Why:
  A 6c jump over 5 ticks corresponds to a meaningful probability shift.
  Confirmation (3 ticks) prevents flash spikes. The 50% retain fraction
  (CONFIRM_RETAIN_FRACTION = 0.5) prevents a spike-and-fall from counting.

Data:
  Signal win rate since live trading began: 5/5 correct direction (Apr 22-24).
  Historical: 22/28 = 79% correct across all paper and live sessions.
  TR2: adding confirmation reduced false signals by ~40% vs TR1.

GATE 6: Minimum current total
  File: signal_engine.py
  Param: --min-current-total (default 4)
---------------------------------------------------------------------------

Rule:
  Skip if (away_score + home_score) < 4.

Why:
  Very low totals (0-3 runs) indicate a pitcher's duel. The Poisson model
  uses average-game lambda values which overestimate P(over) when scoring
  has been suppressed. Scoring pace is correlated — low-scoring games tend
  to stay low-scoring.

Data:
  Paper backtests: total < 4 at signal → WR clustered 55-60%, below break-even.
  Shadow data (2026-04-24): gate_min_current_total shadow outcomes: 2W/0L
  (100% win rate for shadow-would-pass). Small sample (n=2 resolved); not
  enough to justify relaxing. Continue monitoring.

ASK EDGE RAMP — Dynamic min-edge modifier on Gate 8
  File: signal_engine.py  _ask_edge_boost() at line ~251, applied at line ~1944
  Param: --ask-edge-ramp-enabled (default True)
  Param: --ask-edge-ramp-start (default 0.75)
  Param: --ask-edge-ramp-end   (default 0.90)
  Param: --ask-edge-ramp-max-boost (default 0.05)
  Added: Codex (2026-04-25)
---------------------------------------------------------------------------

Rule:
  The base minimum edge (0.15 std / 0.16 high-line) is raised linearly as the
  market ask increases above the ramp-start threshold:

    boost = ((ask - start) / (end - start)) * max_boost   [clamped 0-max_boost]
    effective_min_edge = base_min_edge + boost

  At key ask levels with default params (base=0.15):
    ask <= 0.75: boost=0.000  effective_min_edge=0.150  (no change)
    ask = 0.79:  boost=0.013  effective_min_edge=0.163
    ask = 0.85:  boost=0.033  effective_min_edge=0.183
    ask >= 0.90: boost=0.050  effective_min_edge=0.200  (maximum)

  The boost value is recorded in the candidate payload as min_edge_ask_boost
  and min_edge_effective, so every signal log shows the effective threshold used.

Why:
  When the market is already pricing the over at 75-90 cents, market participants
  broadly agree the over is likely. In this regime, our model edge (FV - ask)
  shrinks toward zero because both sides of the market are converging. A small
  nominal edge at ask=0.85 carries less information than the same edge at ask=0.65
  — the market is nearly as confident as we are, leaving little room for genuine
  model advantage. Requiring more edge in high-ask regimes filters signals where
  we might be riding market momentum rather than model insight.

  Additionally, high-ask signals where the LTP is far below the ask (a common
  pattern: ask=0.81, LTP=0.17 as in BOS@BAL Apr 25) indicate the market
  repriced rapidly after a scoring event. At ask=0.81, we need edge=0.17 vs
  the base 0.15 — a small but meaningful additional filter on these high-ask
  fast-reprice situations.

  The ramp is linear (not step) to avoid creating a hard cliff at a single
  threshold. Marginal signals near the ramp boundary fail gradually rather
  than all at once.

Data:
  Apr 25 fills:
    BOS@BAL ask=0.81: boost=+0.020pp, effective_min=0.170, edge=0.177 — PASSES (barely)
    PHI@ATL ask=0.80: boost=+0.017pp, effective_min=0.167, edge=0.178 — PASSES
    CLE@TOR O7.5 ask=0.68: boost=0, no ramp (below start=0.75)
    CLE@TOR O8.5 ask=0.67: boost=0, no ramp
    ATH@TEX ask=0.76: boost=+0.003pp, effective_min=0.153, edge=0.196 — PASSES easily
  The ramp filtered at the margins on the two high-ask bets. Both won.
  No signals were blocked entirely by the ramp in the Apr 25 session.
  Accumulate 20+ sessions to determine if the ramp thresholds need adjustment.

Shadow verdict:
  No shadow data yet. The ramp modifies gate_min_edge's threshold rather than
  adding a separate skip reason — ramp-affected blocks still appear as
  gate_min_edge in the candidates JSONL, but the min_edge_ask_boost field
  identifies whether the ramp was the deciding factor.

GATE 8f: FV saturation skip
  File: signal_engine.py
  Param: --max-base-fv (default 0.99)
  TR12 (2026-04-22), threshold corrected TR13 (0.98 -> 0.99)
---------------------------------------------------------------------------

Rule:
  Skip if Stage-1 base_fair_value >= 0.99.

Why:
  The Poisson model hits its ceiling (FV → 1.0) when the inferred run lands
  exactly on the line in a late inning with 0 outs. This is the primary
  phantom run fingerprint:
  1. MLB API sends temporary score update.
  2. Model fires at FV~1.0.
  3. Informed Polymarket participants (with faster feeds) sell into our signal.
  4. API corrects — game ends under the line: LOSS.

  Market context matters for interpretation:
  - ask < 0.70: market CONTRADICTS the model (classic phantom — block is critical)
  - ask > 0.85: market CONFIRMS (likely real run, but edge is usually too small
    to bet profitably since edge = FV - ask ~ 0.15 or less; Gate 8 also blocks)
  - ask 0.70-0.85: AMBIGUOUS

  The 0.99 threshold (not 0.98): base_fv=0.9814 fill on 2026-04-20 was a WIN.
  Only near-exact 1.0 saturation is the true phantom fingerprint.

  New logging (2026-04-25): Gate 8f now logs the market ask level and context
  in the skip message so every session shows phantom vs confirmed-run character.

Data:
  STL@MIA O8.5 2026-04-21: base_fv=1.0, ask=0.58, LTP=0.39, LOSS -$31.24.
    Market strongly contradicted model. Largest single live loss.
  2026-04-24 session: 33 gate_fv_saturation blocks. Sample asks: 0.85-0.97.
    Most have base_fv=1.0 exactly. High-ask blocks are market-confirmed real
    runs, but the ask is so high that edge (= FV - ask) is < 0.15, and Gate 8
    (min_edge) would block them anyway. Gate 8f fires first in the pipeline.
  Shadow data: gate_fv_saturation shadow: 0W/0L resolved (1 unknown).
    Shadow relaxed threshold (1.0) blocks all currently blocked signals since
    all have base_fv=1.0 exactly — shadow V2 (0.995) is equally blocked.

GATE 9: Same-event dedup window
  File: signal_engine.py
  Param: --event-dedup-secs (default 60.0)
---------------------------------------------------------------------------

Rule:
  Within 60 seconds of a bet on game_pk X, skip new signals on game_pk X
  UNLESS the new signal has strictly higher edge.

Why:
  One scoring event moves multiple lines simultaneously. Without dedup, we
  take double exposure on a single (potentially phantom) event. Higher-edge
  escape hatch: the best signal on the event wins.

Data:
  2026-04-21 BAL@KC: O8.5 (cancelled, ask reversal) then O10.5 (won +$13.40)
  from same underlying event. Correct: took the better-edge signal.

  File: signal_engine.py
  Param: --inning-dedup-gap (default 2), --inning-dedup-edge-gap (default 0.05)
---------------------------------------------------------------------------

Rule:
  For the same (game_pk, line): skip if fewer than 2 innings since last bet,

PART 2: ORDER-LIFECYCLE GATES (live_engine.py — after order placement)
===========================================================================

These gates run after a limit order has been posted to the Polymarket CLOB
and monitor it for cancellation signals.

---------------------------------------------------------------------------
LIMIT PRICE INVARIANTS
  File: live_engine.py _compute_limit_price()
  Param: --spread-factor (default 0.65)
---------------------------------------------------------------------------

Rule (applied in order):
  1. Crossed/locked book (bid >= ask): return None — cannot place.
  2. Raw limit = bid + spread * spread_factor (0.65).
  3. Cap at fv - min_edge (preserve model edge at fill).
  4. Cap at ask - 0.01 (must be inside spread).
  5. Floor at bid + 0.01 (must improve on best bid).
  6. Round to 2dp (Polymarket minimum tick).
  7. Final: if limit >= ask, return None.
  8. Final: if (fv - limit) < min_edge, return None.

Data:
  DET@CIN 2026-04-24: bid=0.73, ask=0.79, limit=0.77. Ask fell to 0.66
  within 5 seconds (would have been filled at 0.66, better than our limit).
  Order never reached CLOB due to API bug (fixed 2026-04-25).

---------------------------------------------------------------------------
FV DECAY CANCELLATION
  File: live_engine.py _check_fv_decay()
  Param: --fv-cancel-min-edge (default 0.03)   [P0: lowered from 0.05]
  Param: --fv-decay-min-age-secs (default 90s) [P0: extended from 30s]
  Param: --fv-decay-min-ask-drop (default 0.03)
  P0 fixes applied 2026-04-24 based on book-capture analysis of Apr 22 session
---------------------------------------------------------------------------

Rule (four conditions — all required before cancelling):
  0. [NEW P0] Score guard: if current_score_total > bet.line, NEVER cancel.
     The bet has effectively won. Hold until fill or game Final.
  1. Age gate: order must be >= 90 seconds old before FV decay fires.
  2. Model gate: current_fv - limit_price < 0.03 (model edge collapsed to 3pp).
  3. Market gate: entry_ask - current_ask >= 0.03 (ask has confirmed decay).

  If all four pass: cancel. Otherwise hold and log reason.

Why:
  [Score guard] If total already exceeds the line, the bet is a mathematical
  winner. Cancelling would discard realized profit.

  [90s age] Book capture analysis (2026-04-22): the inning-ending repricing
  window — bid collapses at ~13s, LTP resets at ~19s, new equilibrium by
  ~25-45s — takes 60-90 seconds. At 30s the FV decay was firing in the middle
  of that chaos. 90s ensures evaluation happens after market re-equilibrates.

LTP (LAST TRADED PRICE) — DIAGNOSTIC SIGNAL, NOT YET A GATE
  Field: ltp_at_signal (added TR13, 2026-04-25)
  Logged in LIVE BET message as: ltp=X.XXX(gap=+/-X.XXX)
---------------------------------------------------------------------------

The ltp_ask_gap = entry_ask - ltp is now recorded on every placed bet.
Interpretation:
  ltp_ask_gap < 0: buying BELOW last traded price → favorable (market last
    traded higher than we're paying; low adversarial-selection risk)
  ltp_ask_gap 0-0.08: neutral
  ltp_ask_gap > 0.10: buying ABOVE last traded price → potentially risky
    (market hasn't recently confirmed this price; could be stale LTP)
  ltp_ask_gap > 0.30: LTP is likely stale (early-game trade vs current price).
    In this case, LTP is informative — it's just old, not contradictory.

  PHI@CHC 2026-04-23: ltp=0.72, ask=0.69 → gap=-0.03 (buying below LTP).

KELLY SIZING + EDGE CAP
  Param: --stake-mode kelly (default), --kelly-fraction 0.25
  Param: --kelly-max-edge 0.25, --kelly-max-bet-fraction 0.33
---------------------------------------------------------------------------

Formula:
  f* = (fair_value - limit_price) / (1 - limit_price)
  effective_edge = min(edge, kelly_max_edge=0.25)
  stake = effective_f* * daily_budget * kelly_fraction
  stake = clamp(stake, min_order_size, daily_budget * kelly_max_bet_fraction)

Current testing uses --stake-mode flat --stake 15 to isolate fill behavior
from sizing complexity. Switch to Kelly after 15+ fills validate the pipeline.


---------------------------------------------------------------------------
DAILY BUDGET + PER-GAME CAP
  Param: --daily-budget, --per-game-budget-fraction (default 0.35)
---------------------------------------------------------------------------

Rule:
  deployed + reserved must not exceed daily_budget.
  Same-game exposure must not exceed daily_budget * per_game_budget_fraction.

Current testing uses --per-game-budget-fraction 0.40 to allow 2-3 fills per
game while preventing one game from consuming the full session budget.

NOTE: Bug fixed 2026-04-25 — budget tracking previously used live_args.stake
(defaulted to $25) instead of trade_args.stake. This caused DET@CIN session
(2026-04-24) to reserve $25 from a $30 budget after one failed CLOB call,
blocking all 11 subsequent signals with budget_exhausted.
