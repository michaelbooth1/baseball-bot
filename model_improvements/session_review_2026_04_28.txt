PART 2 — WHAT DIDN'T WORK (the concerns)
================================================================================

C1. THE LOSING BET IS A PHANTOM-RUN FINGERPRINT (HIGH PRIORITY)
   Bet 3 (LAA@CWS 7.5):
      score 1-3 in B4, 2 outs, runners empty
      base_fair_value = 0.877  (Stage-1 Poisson said 88% over)
      stage2 +0.089, stage3 -0.132
      final fair_value = 0.872
      entry_ask = 0.57
      edge = 0.302 (!)
      ltp_at_signal = 0.67
      Filled at 0.56, lost (-$20)

   This is the EXACT pattern flagged in our earlier "edge>0.25" analysis
   ("0W/5L on filled bets, all phantom-run cases"). Why did it slip
   through?

      gate_fv_ask_gap: fires only when edge > fv_ask_gap_max(=0.26)
                       AND inning >= fv_ask_gap_min_inning(=7).
      Bet 3 was inning 4 -> the gate did not apply.

   Spot-check Family A on this bet's sidecar:
      ltp_minus_ask_last_3_trades = +0.28
      (recent prints were 28pp ABOVE the ask — strong "market just paid
      a much higher price" signal that the current 0.57 ask might be a
      stale quote about to lift)

   Spot-check Family B:
      book_imbalance_top1 = 0.78  (heavy bid-side — looks bullish for over)
      ask_depth_at_touch = 10     (THIN — easy to clear, suggests
                                   uninformed taker about to take it)

   The microstructure looked PERMISSIVE. The market structurally agreed
   the price should be higher (bid-stacked, recent prints high). But the
   GAME outcome was under (final 7 = exactly the line, lost).

   This is the kind of case where:
   - Stage-1 Poisson cache may overweight the inferred-1-run scenario
     (going from 1-3 to 1-4 in B4 with bases empty pushes Poisson to
     ~88% over — possibly an edge case in the cache calibration)
   - Market knew something the model didn't (possibly the actual run
     was a wild pitch, or the inferred run inference was wrong, or
     the ball/pitcher matchup is unfavorable)
   - Late-game scoring suppression won out

   This is the canonical "informed counterparty fills us" event. Family
   A-E captured it; we now have ONE labeled training row of this
   pattern. We need ~20-30 more before we can tell whether the features
   reliably predict adverse fills.

C2. STL@PIT SHOULD HAVE BEEN A SKIP, NOT A "BUY-AT-LIMIT-NEVER-FILLS"
   Bet 1 (STL@PIT 8.5):
      score 6-1 in B6, runners empty
      edge = 0.205
      ltp_at_signal = 0.24    <-- market last traded at 24 cents
      entry_ask = 0.76
      ltp_minus_ask gap = -0.52  <-- 52pp disconnect
      Posted limit 0.74, NEVER FILLED, cancelled at game_final.
      Counterfactual: WOULD have won (final 18 runs).

   The ask was 0.76 but the LTP was 0.24. Either the book is stale
   (Family A confirms: seconds_since_last_trade=499s ~= 8 minutes since
   last trade) or the bid/ask is from a market-maker quoting wide on a
   thin book.

   Either way, posting a buy at 0.74 against a 0.24 LTP is a low-
   probability fill AND a high-adverse-selection setup if it does fill
   (whoever sells to us at 0.74 over a 0.24 LTP knows something).

   Outcome: order never filled, $0 PnL impact this time. But the
   counterfactual win means we missed a potential $7 gain. Not a loss
   per se, but it shows the gates don't catch the "ask quote is way
   above LTP" pattern. There should probably be a gate:
      if (ask - ltp) > 0.20 AND ltp is recent: skip

C3. PITCHER CACHE BUILD FAILED -> GATE 8i DISABLED ALL SESSION
   2026-04-28 11:05:54 WARNING: pitcher cache build timed out reading
                                 statsapi.mlb.com (15s timeout)
   2026-04-28 11:07:05 WARNING: same timeout, second attempt
   Result: "Gate 8i disabled" for the entire session.

   Gate 8i (pitcher quality boost) raises min_edge by 3pp when the
   current pitcher has ERA < 3.75. With Gate 8i off, ALL bets used the
   non-boosted threshold.

   Bet 3 (LAA@CWS) was inning 4 with the starter likely still in. If
   the starter's ERA < 3.75, the boost would have raised min_edge from
   0.16 -> 0.19 — bet 3 had edge=0.30 so it would have passed anyway,
   but the boost SHOULD have been active.

   Action: pitcher cache build should retry with exponential backoff,
   or fall back to a stale on-disk cache if available, rather than
   silently disabling Gate 8i.

C4. SCHEDULE REFRESH FAILURES (3 INSTANCES)
   2026-04-28 11:06:03, 11:07:14, 18:44:47 — schedule refresh failed
   on three separate occasions due to MLB StatsAPI timeouts /
   connection-aborted. Could have caused brief market-discovery
   misses (market discovery cycle also failed at 18:45:52).

   These auto-recovered (no cascade). But: if a game started during a
   missed-discovery window and the bot didn't pick it up until the
   next cycle, we lost a few minutes of monitoring. Worth quantifying
   if we can.

C5. FAMILY A SIGNED_VOLUME_LAST_30s IS NONE ON 90% OF SKIP CAPTURES
   28/31 sidecars have signed_volume_last_30s=None. Reason: those
   signals fired during stale-market windows (median
   seconds_since_last_trade ~= 200s = 3+ minutes since last trade).

   Not a bug — Family A correctly returns None when no trades occurred
   in the 30s window. But it means signed_volume_last_30s is a sparse
   feature on skip-path data. Most of the fill-model's training will
   get None on this column for skip rows.

   Alternatives to consider (do NOT implement now, just note):
      - Extend the window for skip-path Family A captures to 5 min?
        (Risk: stale info, captures pre-game noise)
      - Add a binary "is_market_stale" feature derived from
        seconds_since_last_trade?
      - Accept None as a categorical "stale" signal and let the model
        learn from it.

   Recommendation: accept the None coverage as informative. The model
   should learn that "stale market at signal time" is itself a regime.

Worth flagging for future analysis as the dataset grows.

PART 5 — IMMEDIATE NEXT STEPS (RANKED)
================================================================================

T-1. HIGH — Extend fv_ask_gap or add a hard edge cap (single biggest fix)
   Bet 3 (-$20) was a textbook phantom-run signature blocked from being
   detected only because fv_ask_gap_min_inning=7. Two options:

   Option A (minimal):
     Lower fv_ask_gap_min_inning from 7 to 4 (or 5).
     Risk: may also block legitimate early-inning high-edge signals.
     Test against history before changing.

   Option B (separate gate):
     Add a "gate_extreme_edge" that fires whenever edge > 0.30
     regardless of inning. Captures the worst phantom-run cases.
     Existing fv_ask_gap (0.26 + inning 7) handles late-inning
     somewhat-large gaps. New gate handles "anywhere, any inning"
     extreme gaps.

   Recommendation: Option B as a safer first step. Easy to tune later.

T-2. HIGH — Add ltp_minus_ask gate
   Bet 1 had a 52pp ltp-vs-ask disconnect. Order didn't fill (correctly
   priced too low for the live market). But trying to BUY at 0.74 over
   an LTP of 0.24 is a phantom-pricing signature. Either the LTP is
   stale (Family A confirms: 8 min since last trade) or the book is
   thin and the ask is a wide quote.

   Proposed gate:
      if abs(ask - ltp) > 0.30 AND ltp_is_recent (e.g. <300s old):
         skip
   This requires Family A to be computed BEFORE the gate — which
   happens at signal time, so we can wire it as a regular gate rather
   than late-stage. Single new gate, ~10 lines.

T-3. MEDIUM — Robust pitcher cache build with retry + fallback
   Current behavior: one timeout -> Gate 8i disabled all session.
   Better: 3 retries with backoff (15s, 30s, 60s); if all fail and a
   stale on-disk cache exists, use it; only disable Gate 8i if no
   cache available at all.
   File: scripts/analysis/build_pitcher_cache.py + signal_engine init
   path that calls it.

T-4. MEDIUM — Tighten schedule refresh resilience
   3 schedule-refresh failures yesterday. Add retry with backoff.
   Quantify whether any games went un-monitored due to discovery gaps.

T-5. LOW — Investigate why bet 1 was placed AT ALL given ltp gap
   The bot placed an order at limit 0.74 against a 0.24 LTP. The
   order naturally never filled. But why did the gates let this
   signal through? Either:
   - The gate stack doesn't currently look at ltp_minus_ask gap (T-2
     would fix)
   - Or the gates DID let it through correctly because the model edge
     was strong enough; the FILLING was the safety net (and worked)
   Either way, a placed-but-never-fills order is wasted budget
   reservation. Track these as a metric.

T-6. LOW — Periodic tick-buffer health log (carry-over from yesterday)
   Family C buffer_n=120 (full) and window_30s_n=12 confirmed working
   for both trade- and skip-path captures. Substrate is healthy. The
   periodic log is no longer URGENT, but still useful for observability.

T-7. LOW — Investigate why bet 1 cancel returned "already canceled"
   Polymarket auto-cancelled the order somehow (probably on game
   resolution). Our cancel path handled it gracefully. Worth a brief
   log scan to understand WHEN Polymarket considers an order
   auto-cancelled. Helps build a mental model for future debugging.
