URGENCY
-------
**Cutover: April 28, 2026 ~11:00 UTC.  ~24 hours from now.**

After cutover:
  - V1 SDKs (py-clob-client, @polymarket/clob-client) STOP FUNCTIONING.
  - All open orders are wiped during the ~1 hour cutover window.
  - V2 takes over the production URL clob.polymarket.com.

This plan is therefore operational, not aspirational. We do not have time
for deliberate multi-week refactoring. The plan is structured as: (1) what
must work tomorrow, (2) what can wait.

PART 2 — WHAT BREAKS
================================================================================

From the migration doc, the breaking changes that matter to us:

1. SDK PACKAGE
   pip:  py-clob-client          ->  py-clob-client-v2==1.0.0
   The V1 package stops working post-cutover.

2. CONSTRUCTOR SIGNATURE
   TS doc shows positional args -> options object, with chainId -> chain.
   Python equivalent unknown without inspecting py-clob-client-v2.
   ASSUMPTION: similar pattern in Python; verify on install.

3. ORDER FIELDS REMOVED
   - taker        (always zero address now, SDK-handled)
   - expiration   (not user-settable)
   - nonce        (replaced by timestamp, SDK-handled)
   - feeRateBps   (operator-set at match time)
   We do not currently set any of these in OrderArgs — confirmed by
   reading polymarket_client.py:place_limit_buy:231-236. Good.

4. ORDER FIELDS ADDED
   - timestamp    (SDK-handled internally)
   - metadata     (bytes32, optional, SDK-handled)
   - builder      (bytes32, for attribution — we do not use)
   - builderCode  (optional per-order — we do not use)

5. EIP-712 DOMAIN VERSION
   Domain version: "1" -> "2"
   verifyingContract addresses change for both standard-risk and neg-risk
   exchanges. Internal to SDK; not our concern.
   Note: ClobAuthDomain (L1 API auth) stays at version "1".

6. CANCELLATION SEMANTICS
   "Onchain cancel replaced with operator-controlled pauseUser/unpauseUser"
   The SDK should still expose a cancel method, but the underlying
   mechanism changed. CRITICAL: verify that py-clob-client-v2 still has
   a callable cancel(order_id) method with similar semantics to V1.
   If not, our cancel_order() needs reworking.

7. COLLATERAL TOKEN MIGRATION (USDC.e -> pUSD)
   "API-only traders: call wrap() on Collateral Onramp contract"
   This is a one-time wallet operation on our funder wallet, NOT a code
   change. If we skip this, orders may fail to settle post-cutover
   because our wallet holds USDC.e and the V2 exchange wants pUSD.
   See: https://polymarket.com/concepts/pusd

8. OPEN ORDERS WIPED AT CUTOVER
   Operational, not code. Our bot only holds orders briefly (3hr safety
   timeout, FV-decay cancel) so there are unlikely to be many open at
   11:00 UTC. We should still pause the bot for the cutover window.

9. BUILDER ATTRIBUTION (HMAC headers REMOVED)
   We never used these. No work.

PART 3 — WHAT (PROBABLY) DOES NOT BREAK
================================================================================

Items the doc does NOT call out as changed, but we should verify after
cutover with a smoke test:

1. PUBLIC GET https://clob.polymarket.com/book?token_id=...
   Doc says "no endpoint paths change." Should work identically.
   Used by: monitor, signal_engine._fetch_depth_snapshot (Family B).

2. PUBLIC GET https://data-api.polymarket.com/trades?market=...
   Doc does not mention data-api.polymarket.com at all.
   "Presumably stable" per the WebFetch summary.
   Used by: tape_capture.py (Family A).

3. PUBLIC GET https://gamma-api.polymarket.com/markets/{market_id}
   Doc does not mention gamma-api. Used as fallback by monitor.

4. WEBSOCKETS (we do not currently use these)
   Doc says URLs unchanged, payloads mostly unchanged.

The risk here is that the doc is silent on data-api / gamma-api but the
backend services may share infrastructure that was migrated. The
post-cutover smoke test must hit all three URLs and confirm 200 + valid
JSON before we resume live trading.

PART 7 — RISK REGISTER
================================================================================

R1. py-clob-client-v2 API surface differs more than expected.
    Mitigation: CP-1 inspection step is non-negotiable. If signatures
    diverge significantly from what this plan assumes, allocate more
    time to CP-2 or accept a few sessions of paper-only operation.
    Severity: HIGH (blocks all live trading).

R2. cancel_order semantics changed.
    The doc's "operator-controlled pauseUser/unpauseUser" wording is
    ambiguous. It MAY mean (a) the SDK still has cancel() but it's
    routed differently, or (b) cancel is no longer per-order and we now
    have to pause our entire account. If (b), our FV-decay cancel logic
    is inoperable.
    Mitigation: test cancel against a real V2 order in CP-4 dry-run if
    possible. If broken, temporarily rely on order-timeout-secs alone
    until we figure out the correct API.
    Severity: MEDIUM (FV-decay cancel is important for adverse-selection
    protection but not strictly required for trading).

R3. pUSD wrap not done before first V2 order.
    Symptom: orders accepted but never settle. Funds stuck.
    Mitigation: CP-3 is mandatory. Verify pUSD balance > 0 BEFORE first
    real order.
    Severity: HIGH (could lose money if filled bets cannot settle).

R4. data-api or gamma-api silently changes.
    Symptom: tape_capture or monitor fail with HTTP errors after cutover.
    Mitigation: smoke test in T+90 minutes step. If broken, Family A
    captures will be empty (already handled gracefully — features dict
    carries None values, sidecar still written, bet flow unaffected).
    Severity: LOW (degrades fill-model data collection, not trading).

R5. Open orders wiped at cutover, our session state thinks they exist.
    Symptom: bot tries to poll an order that the V2 backend has no
    record of; gets "unknown" status and may try to re-cancel forever.
    Mitigation: T-30 minute manual cancel step + ensure live session
    state file is cleared before T+2 restart.
    Severity: MEDIUM (cosmetic but produces noisy logs).

R6. EIP-712 domain swap exposes a stale signed-payload code path.
    Symptom: orders rejected with "invalid signature" errors.
    Mitigation: SDK upgrade should handle this entirely. If we see
    invalid-signature errors post-cutover, the SDK install is wrong or
    cached.
    Severity: LOW (caught immediately by smoke test).

R7. Builder attribution introduced unintentionally.
    We do not use builder attribution, so there's no risk of a
    misconfigured builderCode breaking orders. If we ever add it, must
    use the new per-order field rather than the removed HMAC headers.
    Severity: NONE today.

PART 9 — ROLLBACK PLAN
================================================================================

If V2 migration breaks something we cannot fix in the post-cutover
window, our rollback options are LIMITED because V1 stops working.

Realistic rollback = "stop trading, fix offline." Specifically:

  - Stop live_engine.py
  - Continue running monitor + paper trading (group B endpoints; if
    those work, signal generation continues uninterrupted)
  - Continue running signal_pipeline against new market data — Family
    A/B/C/D/E features keep accumulating in candidate_universe even
    without bets being placed
  - Fix polymarket_client.py at leisure
  - Resume live trading once smoke test passes

Loss in this scenario: trading P&L for the affected session(s). We do
NOT lose data-collection runway because the public APIs continue
feeding the candidate universe.
